Getting Started

Core Concepts

What Ginie is

Ginie is an AI pipeline that accepts plain English descriptions and produces deployed Canton smart contracts. It is not a code editor. It is not an AI assistant. It is a fully automated deployment system where the output is a live Contract ID on a Canton ledger — not code to copy-paste.

GinieNet

GinieNet is a public Canton sandbox operated by BlockX AI. Any user can deploy contracts to GinieNet without DevNet credentials or a Canton account. Every Contract ID on GinieNet is real — verifiable on CantonScan. GinieNet is intended for prototyping and evaluation.

Daml and Canton — brief context

Daml is a smart contract language built for financial workflows. Canton Network is the blockchain that runs Daml contracts. Normally, writing and deploying a Daml contract requires learning Daml (a Haskell-derived language with strict type rules and party semantics), installing the Canton SDK, and running several CLI commands. Ginie handles all of this for you.

⚠️
Scope
Ginie generates single-module contracts of 50–200 lines — IOUs, bonds, repos, DvP, custody, multi-party settlements. It does not generate multi-module enterprise Daml packages or daml-finance interface extensions. See Scope & Limitations for the full picture.

The Daml SDK Ginie uses

All contracts are compiled with Canton SDK 3.4 using dpm build and dpm test — the official Digital Asset package manager. The Canton JSON Ledger API (port 7575) handles deployment. Every generated daml.yaml targets Canton SDK 3.4.

Stage-by-stage breakdown

01 — Intent Agent

Parses your plain English prompt into a structured JSON contract specification. Identifies templates, parties, choices, fields, and preconditions. This spec is the input for the RAG layer and Writer Agent.

02 — RAG Layer

Retrieves the most relevant Daml patterns from the institutional pattern library (ChromaDB vector store). The retrieved patterns inform the Writer Agent's generation — providing idiomatic Daml structure for the contract type you're building.

03 — Writer Agent

Generates a complete, idiomatic Daml module based on the intent spec and retrieved patterns. The output follows Canton SDK 3.4 conventions: correct signatory/observer/controller structure, proper choice syntax, SCU-aware field design.

04 — Compile Agent

Runs the real dpm build command against the generated Daml source. This is not a linter or syntax check — it is the actual Canton SDK compiler. If compilation fails, the error output is passed to the Fix Agent.

05 — Fix Agent

Handles compilation errors automatically. The Fix Agent recognises 11 error types and applies targeted fixes — not re-prompting from scratch. It retries up to 3 times before returning an error to the user.

Error typeExampleFix approach
Missing signatoryTemplate has no signatoriesAdds signatory from first party in spec
Type mismatchExpected Party, got TextCorrects type annotation
Unbound variableVariable 'amount' not in scopeAdds field to template record
Missing importUnknown module DA.DateAdds missing import statement
Choice return typeExpected ContractId, got ()Wraps return in correct type

06 — Audit Layer

Runs the 5-gate pre-deployment security scan. See Audit Layer for the full gate documentation. Any CRITICAL finding blocks deployment and returns the finding to you with a specific explanation.

07 — Deploy Agent

Uploads the compiled DAR to Canton Ledger API, allocates the party, and returns the Contract ID and CantonScan link. The deploy target is determined by your selected ledger: ginienet, localnet, or mainnet.

How It Works

RAG & Pattern Library

The RAG (Retrieval-Augmented Generation) layer is what makes Ginie's Daml output idiomatic. Instead of generating from scratch, the Writer Agent retrieves the closest matching patterns from a curated library of validated institutional Daml contracts.

What's in the pattern library

The library is sourced from production-grade Daml repositories and validated by senior Daml engineers against Canton SDK 3.4:

  • digital-asset/daml — official Daml examples and stdlib patterns
  • digital-asset/daml-finance — financial instrument templates (bond, repo, DvP, cash)
  • digital-asset/splice — Splice protocol patterns and Canton utilities
  • digital-asset/cn-quickstart — Canton application scaffolding patterns
  • digital-asset/ex-models — extended Daml model examples
  • Community-contributed patterns via Canton Skills (MIT, Apache 2.0)

Canton Skills

Canton Skills is a separately published npm package (npx canton-skills install) that provides a structured knowledge base for AI coding agents. It covers Canton SDK 3.4, Splice 0.5.0, DPM, CIP-0103, CIP-0056, PQS, TypeScript frontend patterns, and deprecated API guardrails. In Ginie, Canton Skills functions as the primary knowledge layer for both the Writer Agent and Fix Agent.

✅
Using Canton Skills independently
Canton Skills works standalone. If you use Claude Code, Codex, or Cursor to write Daml, run npx canton-skills install to give your AI assistant the same Canton knowledge base Ginie uses internally.
How It Works

Audit Layer

Every Ginie-generated contract passes a 5-gate pre-deployment security scan before any DAR is uploaded to the Canton ledger. A single CRITICAL finding blocks deployment entirely. The finding is returned to you with a specific, line-level explanation.

💡
The audit layer is what separates AI-generated Daml from manually-written Daml in terms of safety. AI models have specific failure modes — particularly around Canton's party and authorization model. The gates are designed around these known failure modes.
Gate 1
Signatory presence check — CRITICAL
Every template must have at least one signatory. A template with zero signatories cannot create contracts on Canton — deployment would succeed but the contract would be unusable.
CRITICAL: Template Bond has no signatories — contracts cannot be created on this template.
Gate 2
Controller–signatory validation — CRITICAL
Choice controllers must appear in the template's signatories (or be explicitly justified with an observer pattern). A controller not in signatories can exercise a choice without the asset owner's authorization — a critical vulnerability.
CRITICAL: Choice Iou_Transfer: controller Alice is not in signatories. This choice can be exercised without asset owner authorization. Deployment blocked.
Gate 3
Unguarded choice analysis — WARNING
Choices without ensure clauses that could be exercised in invalid contract states. These generate warnings, not blocks — the contract deploys but the finding is returned so you can evaluate the risk.
WARNING: Choice Settle has no ensure clause — may execute on contracts in an invalid settlement state.
Gate 4
Known anti-pattern matching — WARNING
Checks for hardcoded party strings, missing divulgence controls, non-atomic workflows, and other known Daml anti-patterns. Generates warnings on findings.
WARNING: Hardcoded party string "Alice" found in template — use a parameter instead for reusability.
Gate 5
SCU upgrade compatibility — INFO / CRITICAL
Validates that the generated contract follows Smart Contract Upgrade (SCU) rules — additive-only field structure, correct @daml.upgrade annotation usage, valid version string format. Every export includes UPGRADE_NOTES.md.
UPGRADE_FAIL: Field 'maturityDate' removed from Bond template — non-additive change blocks SCU compatibility. Deployment blocked.

What happens when a gate fails

CRITICAL findings (Gates 1, 2, and 5 on certain findings) block deployment. The pipeline stops, and you receive the specific finding with a recommended fix. You can then iterate on your prompt to resolve the issue — Ginie will regenerate with awareness of the previous finding.

WARNING findings (Gates 3, 4, and Gate 5 on non-critical findings) do not block deployment. They are returned alongside the Contract ID so you can make an informed decision about whether to act on them.

Reading the audit report

The full audit report is returned with every successful deployment and is included in the project export bundle as AUDIT_REPORT.md. In the M2 GitHub integration, the audit report is also automatically posted as a comment on every pull request.

How It Works

SCU Compatibility

Smart Contract Upgrade (SCU) is Canton's on-chain contract upgrade mechanism. Every Ginie-generated contract is SCU-compatible from the first deployment — meaning it can be upgraded on-chain without downtime or manual migration of active contracts.

Why this matters

A contract that was not designed for SCU from the start cannot be upgraded on Canton without first archiving all active contracts and recreating them under the new template. For production financial systems, this means taking a workflow offline. SCU eliminates this entirely — but only if the original contract was built correctly.

What Ginie enforces by default

  • All new fields added to templates are Optional — new fields cannot break existing contracts
  • No field removals or renames — additive-only evolution
  • @daml.upgrade annotation structure is applied to upgrading modules
  • daml.yaml version string uses proper semver format — not hardcoded 0.0.1
  • Every export bundle includes UPGRADE_NOTES.md documenting the upgrade path

The SCU Upgrade Agent (M2)

When you need to modify an already-deployed contract, the SCU Upgrade Agent handles the upgrade lifecycle. You provide your existing .daml source, the current version, and a description of your modification. The agent generates the upgraded version, validates it is additive-only, bumps the daml.yaml version, and produces both the upgraded contract and an UPGRADE_NOTES.md.

python
# M2+ — Upgrade an existing deployed contract
result = client.upgrade(
    source_file="./Bond.daml",
    current_version="0.0.1",
    modification="add an optional maturityExtension field of type Optional Date"
)

# result.new_source      — upgraded .daml with upgradeFrom annotation
# result.daml_yaml       — bumped to version 0.0.2
# result.upgrade_notes   — UPGRADE_NOTES.md for active contract migration
# result.validation      — confirms additive-only change

Scope & Limitations

Ginie is honest about what it does and doesn't do. Understanding these boundaries will help you decide when Ginie is the right tool.

What Ginie handles well

  • Single-module Daml contracts of 50–200 lines
  • Bilateral and 2–3 party workflows
  • Standard financial contract patterns: IOU, bond, repo, DvP, custody, AML, settlement
  • Standard choice structures: transfer, settle, archive, propose/accept
  • SCU-safe contracts designed for on-chain upgrade from day one
  • Full project export — contracts you can own, maintain, and extend independently

Current limitations

⚠️
Known boundaries
No cross-module imports. Each generated module is standalone. Multi-module Daml packages with cross-references are not yet supported.

No daml-finance interface extensions. Ginie cannot generate contracts that extend Daml.Finance.Interface.* types. This is on the M3 roadmap.

Ginie is not a replacement for a Daml engineer on production-grade bespoke contracts. It generates the starting point — the prototype that a Daml team then owns and extends.

What Ginie is not

  • Not a cloud IDE or terminal emulator
  • Not a Daml language assistant or documentation chatbot
  • Not a replacement for Daml Autopilot (which serves existing Daml developers)
  • Not a replacement for splice or multi-module enterprise Daml packages

FAQ

Do I need a Canton account or credentials?

No. GinieNet is a public Canton sandbox — you can deploy contracts without any credentials. For deploying to Canton Mainnet or your own LocalNet, you will need the appropriate Canton party credentials.

What LLM does Ginie use?

Claude Sonnet is the default — it produces the highest first-pass Daml compile rates in Ginie's production benchmark. You can switch to GPT-4o, Gemini 2.5 Flash, or (from M4) Ginie-1 using the llm parameter in the SDK or the model selector in the web UI.

Is my contract source code stored?

Generated Daml source and audit reports are stored temporarily for the duration of a session. With the M2 GitHub integration, your code is committed to a repository you own and control. On GinieNet, Contract IDs are stored for explorer access. You can delete your data via the dashboard.

Can I use Ginie with my own Canton node?

Yes. Set CANTON_LEDGER_HOST in your environment to point at your own Canton participant node. The deploy agent will target your node instead of GinieNet. Fully supported in self-hosted deployments.

What happens if compilation fails after 3 retries?

The pipeline returns the final compiler error alongside the generated Daml source so you can inspect what went wrong. You can then iterate with a more specific prompt or modify the source directly. In most cases, rephrasing the prompt with more explicit party and choice structure resolves the failure.

Is the audit layer audited itself?

The audit layer is open-source (Apache 2.0) and peer-reviewed by an external Daml specialist who validates each gate against real-world Canton vulnerability patterns. An external security audit of the full system (including auth, job isolation, JWT) is on the M3 roadmap.

Can I contribute Daml patterns to the RAG library?

Yes. Submit a PR to Canton Skills — the MIT-licensed companion library. Every merged pattern is validated against Canton SDK 3.4 by CI before entering the corpus. Merged patterns automatically propagate to Ginie's RAG layer via the POST /admin/refresh-rag endpoint.
